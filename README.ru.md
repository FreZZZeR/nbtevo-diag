# nbtevo-diag

> **Язык:** [English](README.md) · Русский — как добавить язык, см. [TRANSLATING.md](TRANSLATING.md).

Диагностика **из головного устройства BMW NBT EVO** (собрана под **F30 335d**, дизель N57, iDrive6):
коды неисправностей по модулям и живые датчики двигателя/автомобиля — **прямо в iDrive, без
OBD-адаптера**. Голова уже стоит на диагностической сети машины и достаёт каждый модуль через шлюз
FEM по HSFZ/UDS — на той же плоскости, где говорит evocode. Без донгла, без телефона.

> Только своя машина, по локальному подключению. Чтение безопасно; единственная запись (сброс DTC)
> закрыта флагом `--commit`. Кодировку, FSC и прошивку не трогает.

## Архитектура (3 слоя)

1. **HMI-плагин** — меню iDrive с разделами **Ошибки** (DTC) и **Датчики**. Нативный C++/QNX;
   plugin ABI из NBT-EVO toolkit SDK / NBT-AAD. Визуальный ориентир — деки BoostDeck/ShiftDeck.
2. **Коллектор** — C-воркер на голове, опрашивает внутренний шлюз (HSFZ 6801 → UDS) и кормит плагин.
   Образец: `collector.c` из ID6_apps.
3. **Движок данных** — карта DID, математика декодирования и логика DTC. **Этот репозиторий, на
   Python, и есть тот движок** (Phase 0), построенный на транспорте evocode — чтобы его можно было
   разрабатывать и *обнаруживать* сигналы с ноутбука по ENET ещё до появления нативного кода.

**Phase 0 (сейчас):** Python-движок + CLI — читать DTC, читать уже известные сигналы и
**пробивать/валидировать реальные DID для N57** → получить per-car карту. Нулевой риск кирпича, без
тулчейна. **Phase 1 (позже, нужен QNX SDP 6.5 + ARM GCC 4.4.2):** перенести движок в нативный
коллектор + HMI-плагин, чтобы он работал из iDrive.

## Факты о транспорте (из RE тулкита)

- Один сокет к **шлюзу FEM `0x10`** достаёт каждый модуль по **целевому байту UDS** (HSFZ, не DoIP;
  без routing-activation). DDE `0x12`, EGS `0x18`, голова `0x63`.
- Список модулей за один заход: функциональный TesterPresent `3E 00` → `0xDF`, каждый живой ECU
  отвечает `7E`.
- **DTC:** `19 02 FF` по модулю, сессия по умолчанию, без SecurityAccess. Сброс: `14 FF FF FF`.
- Живые значения: стандартные OBD mode-01 PID и BMW-специфичные DID через `22`.

## Установка и использование (Phase 0, с dev-машины по ENET)

```bash
pip install nbtevo-diag                 # ядро: диагностика по ENET (тянет evocode)
pip install "nbtevo-diag[deploy]"       # + evocode[ssh]/paramiko, чтобы доставить приложение на голову
# или из чекаута:  pip install -e .

nbtevo-diag catalog                          # каталог сигналов (офлайн, без машины)
nbtevo-diag sgbd    FILE.prg --params        # прочитать EDIABAS SGBD -> каталог DID (UDS-22, офлайн)
nbtevo-diag modules --host 169.254.x.x       # перечислить живые ECU
nbtevo-diag dtc     --host 169.254.x.x       # прочитать память неисправностей (все модули)
nbtevo-diag live    --host 169.254.x.x       # coolant/oil/boost/power/... вживую
nbtevo-diag scan    --host 169.254.x.x --ecu 0x12 --hunt   # обнаружить DID для N57
```

`--host` — IP шлюза FEM (ENET ident-броадкаст / discovery в evocode).

## Каталог сигналов — и что людям на самом деле нужно

`nbtevo_diag/signals.py` — единый источник правды. У каждого сигнала есть **confidence**:

- **✓ standard** — SAE J1979 OBD mode-01. Работает на дизеле, формулы стандартизированы, проверяется
  сразу. Это уже закрывает добрую часть списка «приборка + OBD»: **coolant, oil temp, intake air,
  ambient, RPM, speed, MAP/boost, MAF, load, throttle, pedal, timing, fuel rate & level, напряжение
  модуля, commanded EGR, run time**, и — числа «спортивных дисплеев» — **actual torque %, reference
  torque (Нм) и power** (крутящий × обороты).
- **ƒ computed** — **boost** (MAP − baro, бар/psi), **torque** (Нм), **power** (кВт/л.с.).
- **? bmw-candidate** — BMW-DID из **бензинового** референса B58/340i (ID6_apps). *Шаблон*, не
  валидный для N57 до проверки: boost/ambient `4205`/`4201`, rail `56D7`, oil-press `586F`, coolant
  `4300`, trans-temp `DA12` (EGS). NB: скейл rail — под бензиновый GDI, для common-rail неверен.
- **· probe** — нужно, но адрес/декод неизвестны → показывается **n/a** до обнаружения: **давление
  рейла, давление масла** (на N57 может быть только датчик-выключатель), **обороты турбины,
  VGT/вейстгейт, цикловая подача, EGT, нагар DPF / регенерация / дифф-давление, уровень AdBlue
  (SCR)**, и — другие модули — **износ тормозных колодок, TPMS, пункты CBS**.

Часто хотят сверх этого списка (улица/трек/быт), уже сгруппировано в каталоге: **нагар и
регенерация DPF и AdBlue** (критично для дизеля), **температура АКП** (трек), **EGT**, **напряжение
АКБ**, **расход/запас топлива**, **давление в шинах**, **остаток по CBS**. Вычисляемые добавки под
Phase 1 из скорости/времени: **0–100 км/ч, ¼ мили, таймер круга, G-метр**.

Обнаруженная per-car правда идёт в `maps/<car>.json` (gitignored) — каталог держит метод +
кандидатов; проверенные DID/скейлы конкретной машины живут в её карте. Значение показывается только
после валидации по независимому источнику (ISTA / приборка / логгер); иначе остаётся **n/a**, а не
врёт.

## Тесты без машины

`python -m pytest tests/` (или `python tests/test_signals.py`) гоняет чистые проверки — целостность
каталога и математику декодирования — без машины и без evocode. **IDEmu этот слой не проверяет:**
эмулятор не выставляет диагностическую точку HSFZ (6801), поэтому полезен только позже для рендеринга
HMI-плагина, не для движка данных. Движок данных валидируется на машине (или на mock-шлюзе).

## Управление xDrive — актуация с программным предохранителем

Сверх read-only диагностики включена одна **актуация**: xDelete-подобный **временный задний привод**
(портирован из ID6_apps). DSC (`0x29`) командует раздаткой через `2E DB E1 <0=RWD | 1=AWD>`, после
проверки варианта + возможности, с read-back режима.

Референс отказывает в записи, если машина не стоит, не в Park **и двигатель не заглушён** — и в форме
BM3 последнее лишь ярлык, который человеку доверено соблюдать. Здесь каждое условие —
**предохранитель в коде** (`control.py`), включая engine-off:

- включение RWD требует **полной остановки (speed = 0)** — порог, который **не** обходится;
- Park требуется по умолчанию (`--no-park-check` снимает; полная остановка всё равно держится);
- **engine-off — дефолт**, обеспечен в коде — не выброшен, не ярлык. Снять **осознанно** флагом
  `--allow-running` (остановка + Park всё равно держатся). Остаётся дефолтом, потому что запись
  латч-подобна (DSC `0x0F2510` возвращает AWD только циклом зажигания), а модуль трактует RWD как
  degraded-состояние — заглушённый двигатель и есть тот спокойный момент с нулевым крутящим на
  трансмиссии, которого ждёт контроллер;
- **dry-run по умолчанию**; реальная запись требует `--commit`, который дополнительно **закрыт
  VIN-гейтом** (`NBTEVO_OWN_VIN`); результат считывается обратно для подтверждения; AWD
  восстанавливается циклом зажигания.

```bash
nbtevo-diag xdrive --host IP status          # вариант / режим / скорость / park / двигатель
nbtevo-diag xdrive --host IP rwd             # dry-run: план + результат блокировок
NBTEVO_OWN_VIN=<твой VIN> nbtevo-diag xdrive --host IP rwd --commit                  # включить RWD (стоя, Park, двигатель заглушён)
NBTEVO_OWN_VIN=<твой VIN> nbtevo-diag xdrive --host IP rwd --commit --allow-running  # ...с работающим двигателем, осознанно
nbtevo-diag xdrive --host IP awd --commit    # восстановить AWD
```

> ⚠ Отключение передней оси меняет поведение машины (тяга, DSC/ABS). Только трек / частная
> территория, никогда на дороге общего пользования, на своей машине, на свой риск. Поддержаны две
> версии DSC: 340i-style (`0x0F2510`/`0x0F2850`, двигатель **заглушён**) и **DSC_25 F30 N57 (`0x0F1860`)**
> — включать с **работающим** двигателем, режим читается с раздатки LMV (`0x19`). Путь DSC_25 подтверждён
> заводскими SGBD ISTA (`dsc_25.prg` + `lmv_01.prg`); всё равно проверь read-back на машине
> (upstream #68 сообщает, что `0x0F1860` может не включаться).

## Деплой — доставить нативное приложение на голову

Он-кар слой ([nbtevo-id6-apps](https://github.com/FreZZZeR/nbtevo-id6-apps): коллектор + HMI-плагин)
**доставляется этим Python-слоем**, а не форком чьего-то инсталлятора. `deploy.py` делает две вещи,
обе обратимые и dry-run по умолчанию:

- **Координация 6801-lease.** Он-кар коллекторы держат приватный loopback-lease на единственном
  диагностическом шлюзе (TCP 6801), который ноутбук не видит, — поэтому гонять evocode/diag при живом
  коллекторе = взаимные таймауты. `deploy` (и любая диагностическая сессия) **ставит коллекторы на
  паузу** на своё время и перезапускает их после (`collectors_paused`).
- **Безопасная многофайловая установка** по dev-SSH головы, повторяя хореографию `fw` из evocode
  (сначала бэкап `.orig` → загрузка temp на тот же раздел → сверка числа байт на устройстве →
  атомарный rename-over → chmod), и **всё-или-ничего**: любой сбой откатывает весь набор.

```bash
# dry-run (ничего не пишет): показать план + шаги lease
nbtevo-diag deploy --host IP  build/libNbtGauges.so:/var/opt/hmi/data/ID5/Plugins/Gauges/libNbtGauges.so \
                              --collector nbtevo-collector --restart appreset
# выполнить (VIN-гейт), поставив названный коллектор на паузу на время передачи
NBTEVO_OWN_VIN=<твой VIN> nbtevo-diag deploy --host IP ... --collector nbtevo-collector \
                              --start-collectors "/var/opt/car/bin/nbtevo-collector &" --commit
nbtevo-diag deploy-revert --host IP /var/opt/hmi/data/ID5/Plugins/Gauges/libNbtGauges.so --commit
```

> Путь записи **ещё не прогнан на живой голове** (есть только хост-тесты против фейкового устройства).
> Имена процессов коллектора задаёшь ты — они принадлежат он-кар приложению, не захардкожены.
> `--restart appreset` перезапускает только HMI (с верификацией по PID — на части голов appreset
> возвращает 0, не ресетнув); для полной штатной перечитки без power-cycle используй `evocode reset`
> (UDS 11 01).
